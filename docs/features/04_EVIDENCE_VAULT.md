# Feature 04: Cryptographic Evidence Vault & Provenance DAG

## 1. Overview & Forensic Objective

The **Cryptographic Evidence Vault** transforms the SIH26182 VASP Attribution Engine from a standard visualization tool into a court-admissible, tamper-evident forensic intelligence platform. 

In traditional digital forensics, screenshots or loose database dumps lack chain-of-custody validity. Under **Section 63 of the Bharatiya Sakshya Adhiniyam, 2023 (BSA)** (which replaces Section 65B of the Indian Evidence Act), electronic records must prove that:
1. The computer system was operating properly and deterministically.
2. The records have not been modified, replaced, or tampered with since collection.
3. Every high-level inference (e.g., "Address X is a Binance deposit hot-wallet") can be mathematically and bidirectionally traced back to primary on-chain consensus transactions.

To satisfy these statutory burdens, the Evidence Vault organizes all analytical observations into a **tamper-evident Directed Acyclic Graph (DAG)** secured by **RFC-8785 JSON Canonicalization Scheme (JCS)** and **SHA-256 cryptographic hash chaining**.

---

## 2. 4-Tier Evidentiary Classification Scheme

Every item stored in the Evidence Vault is strictly categorized into one of four standardized legal tiers:

```
[OBSERVED: Primary Consensus Events]
        │
        ▼ (Deterministic Math)
[DERIVED: Behavioral & Topology Metrics]
        │
        ▼ (Statistical / GNN Heuristics)
[INFERRED: VASP Attribution & Entity Profiles]
        │
        ▼ (Officer Review & Sign-Off)
[HUMAN_ACTION: Legal Preservations & Notices]
```

### Tier 1: `OBSERVED` (Primary On-Chain Facts)
- **Definition:** Immutable transaction events fetched directly from blockchain consensus RPC nodes (Etherscan, Alchemy, TronScan, TronGrid).
- **Properties:** Cannot be contested. Contains raw tx_hash, block_number, block_timestamp, from_address, to_address, value, and asset type.
- **Example:** `Tx 0x3f552... transferred 50,000 USDT from 0xSuspect to 0xIntermediate at Block 21894210`.

### Tier 2: `DERIVED` (Deterministic Computational Metrics)
- **Definition:** Mathematical calculations computed directly from `OBSERVED` records without heuristic speculation.
- **Properties:** 100% reproducible by any third-party forensic expert given the same raw inputs.
- **Examples:** 
  - Consolidation sweep ratio (e.g., `99.4%` of received funds forwarded in single tx).
  - Time delta between inbound and outbound transfers ($\Delta t = 842\text{ seconds}$).
  - Fan-in counterparty convergence count ($k = 14$ distinct senders).
  - Graph topological metrics (in-degree, out-degree, centrality).

### Tier 3: `INFERRED` (Analytical Hypotheses & Probabilistic Attributions)
- **Definition:** Conclusions generated by the VASP Attribution Engine, GNN classifier, or peel-chain detector.
- **Properties:** Probabilistic. Requires human verification before statutory action.
- **Examples:**
  - Attribution hypothesis linking candidate address `0x71660...` to `Coinbase Hot Wallet 4` with confidence `0.84`.
  - GNN GraphSAGE classification tagging node `0x9045e...` as `mixer` with probability `0.88`.

### Tier 4: `HUMAN_ACTION` (Investigator Decisions & Procedural Actions)
- **Definition:** Formal actions taken by the Investigating Officer (IO) or Forensic Analyst within the system.
- **Properties:** Establishes procedural chain-of-custody.
- **Examples:**
  - Officer notes appended during investigation.
  - Officer acceptance or dismissal of an attribution hypothesis.
  - Generation of a Section 94 BNSS preservation notice.
  - Generation of a Section 63 BSA evidence certificate.

## 3. Cryptographic Hash Chain Architecture & RFC-8785

### The Non-Deterministic JSON Problem
Standard JSON serializers (Python `json.dumps`, JavaScript `JSON.stringify`) produce non-deterministic strings based on:
- Unordered dictionary keys (`{"a":1,"b":2}` vs `{"b":2,"a":1}`).
- Arbitrary whitespace and indentation.
- Floating-point representations (`1.0` vs `1`).

Calculating SHA-256 on non-canonical JSON produces different hashes for identical data, destroying forensic integrity.

### RFC-8785 Canonical Serialization
Before computing SHA-256, all payloads are canonicalized using **RFC-8785 (JSON Canonicalization Scheme)**:
1. Keys are lexicographically sorted by Unicode codepoint.
2. Whitespace outside of strings is eliminated.
3. Strings are UTF-8 normalized.
4. Floats are serialized per ECMAScript specification without trailing zeroes.

### Recursive Hash Chaining
Each evidence record is chained to the preceding evidence record within the case:

$$\text{ContentHash}_i = \text{SHA256}\left(\text{RFC8785}(\text{Payload}_i)\right)$$

$$\text{ChainHash}_i = \text{SHA256}\left(\text{ChainHash}_{i-1} \parallel \text{ContentHash}_i \parallel \text{Timestamp}_i \parallel \text{ActorID}_i\right)$$

Where:
- $\text{ChainHash}_0 = \text{SHA256}(\text{"GENESIS\_CASE\_" } \parallel \text{CaseID})$
- Any modification of a historical record breaks the hash chain at sequence $i$ and invalidates all subsequent hashes $i+1 \dots N$.

## 5. Canonicalization & Hashing Implementation

```python
# backend/app/core/canonical_hasher.py
import hashlib
import json
from typing import Dict, Any


def rfc8785_canonicalize(data: Dict[str, Any]) -> bytes:
    """
    Implements RFC-8785 JSON Canonicalization Scheme (JCS).
    Lexicographically sorts keys, strips non-essential whitespace, ensures UTF-8.
    """
    return json.dumps(
        data,
        sort_keys=True,
        separators=(',', ':'),
        ensure_ascii=False
    ).encode('utf-8')


def compute_content_hash(payload: Dict[str, Any]) -> str:
    """Computes SHA-256 digest of RFC-8785 canonical JSON payload."""
    canonical_bytes = rfc8785_canonicalize(payload)
    return hashlib.sha256(canonical_bytes).hexdigest()


def compute_chain_hash(
    prev_chain_hash: str,
    content_hash: str,
    timestamp_iso: str,
    actor_id: str
) -> str:
    """
    Computes chained cryptographic hash:
    ChainHash_i = SHA256(ChainHash_{i-1} + ContentHash_i + Timestamp_i + ActorID_i)
    """
    composite = f"{prev_chain_hash}:{content_hash}:{timestamp_iso}:{actor_id}"
    return hashlib.sha256(composite.encode('utf-8')).hexdigest()
```

### 2. Verify Case Integrity
- **Endpoint:** `GET /api/v1/cases/{case_id}/evidence/verify-integrity`
- **Logic:**
  1. Walks the evidence list from sequence 1 to $N$.
  2. For each item, recomputes `content_hash = SHA256(canonicalize(payload))`.
  3. Recomputes `expected_chain_hash = SHA256(prev + content_hash + ts + actor)`.
  4. If mismatch found, halts and returns `is_valid: false`, `corrupted_sequence_number: i`.
  5. If entire chain validates, returns `is_valid: true`.

## 8. Automated Pipeline Ingestion

When a trace finishes in `tracer.py`, the backend automatically generates:
1. **`OBSERVED` records** for each transaction in the traced path.
2. **`DERIVED` records** for:
   - Peel-chain detection status and value differences.
   - Consolidation sweep ratio at the penultimate node.
3. **`INFERRED` record** for the final VASP Attribution (linking candidate deposit wallet to exchange hot wallet with confidence breakdown).

This ensures no investigator has to manually enter data to get a comprehensive, court-ready Evidence DAG.
